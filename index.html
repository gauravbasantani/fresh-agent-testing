How I test AI with fresh agents

AI output can look finished and still be wrong. I test it with AI agents that have never seen the work, then check what they made with tools, not just my eyes. I've used this method twice. Here is how it works and what it found.

The problem

The worst AI mistakes don't look like mistakes. The page renders. The video plays. The numbers are formatted. And something is still wrong:

  • a rule that means one thing in step 2 and another in step 5,
  • a label in a brand color nobody can read,
  • markup that looks fine on screen and breaks for a screen reader.

A reviewer who already knows the work reads past these. Someone new, or something new, runs straight into them.

The method in 5 steps

  1. Write down the mistakes that matter. Before testing, list the mistakes that would look finished and be wrong. Those are what you count.
  2. Start every agent fresh. Each test agent gets a clean copy of the project and no context. It knows only what a new user or a new developer would know.
  3. Give it a real job, more than once. Same task, several runs. When you're testing whether something helps, run with it and without it, and change nothing else.
  4. Check the output with tools. Full builds, accessibility checks, measured contrast, lint rules. Count findings by type. Report the numbers as they came out.
  5. Fix, then verify each fix on its own. A fix isn't done because someone said so. Check it, then run fresh agents again.

Study 1: LIVE

Fresh agents found contradictions no reviewer had noticed.

LIVE is an AI video workspace for short teaching videos at ASU's Learning Engineering Institute. People talk to an AI assistant and get a styled, captioned video, with no editing software. It is a three-designer project. I wrote the instructions and skills the AI follows: the 8-step video conversation, the ASU style, captions and narration skills, setup and permissions, and worked examples.

How I tested it

Before anyone new touched it, fresh AI agents with no context played the new user, in clean copies of the project, across two rounds.

  • 8fresh AI agents as new users
  • 2rounds
  • 17defects in the first full build
  • 12findings in the second

All of them are closed. One example: "short" meant 30 seconds in one step and 60 in another. Now there is one definition, used everywhere.

Measured, not assumed

ASU's secondary colors were measured against the page, not assumed. 4 of 7 fail even the 3:1 minimum for shapes. So the style skill uses them for fills only, never for text or labels.

LIVE's code is private, so this page describes the method and results only.

Study 2: Proposal kit

Rules built into the components did the work. The docs had almost nothing left to prevent.

The Proposal kit is a tiny design system for one solar proposal summary, with made-up data. I designed it and directed Claude Code, which wrote the code. I wanted to know whether AI-facing docs stop an AI coding tool from making costly mistakes.

How I tested it

20 fresh claude -p runs built the same page from the same prompt. Half got the kit's AI docs, half didn't. Each run worked in its own copy, with no tests or lint rules to copy from. Then the same checks ran on every output, counting five mistake types.

What happened

  • Types 1 to 4 never happened, with or without the docs. No price typed as text, no payment without its rate and term, no hardcoded colors or sizes, no savings without "Estimated". Every run read the components, and the required props made those mistakes hard to make.
  • One accessibility slip got through: a divider placed inside a definition list. It looked fine on screen. It showed up in 5 of 10 runs without the docs and 1 of 10 with them.

That is not proof the docs helped. The docs never mention this mistake, and 5 runs per group in each round is a small sample. What it does show: the checks caught a real mistake a person reviewing the screen would miss.

The next step, not done yet, is a rule that stops the divider from going inside a list at all.

What I'd do at a company in week one

  1. List the mistakes that cost the most. With the team, write down the five errors in your product that look finished and are wrong.
  2. Run fresh agents on one real path. A new user's first task, or an AI tool building a screen from your design system. Clean copies, no context.
  3. Add one check for what got through. A lint rule, an accessibility test, a required prop. Something that runs every time, not a note in the docs.
  4. Share the raw numbers. What was found, what was fixed, what is still open. No rounding up.
